# はじめに

microCMS では、バックエンド（Go / Node.js）やフロントエンド（React / TypeScript）、インフラ（OpenTofu / Terragrunt）、その他諸々を 1 つのモノレポで管理しています。

1 つのリポジトリで完結するのは、横断的な変更もコーディングエージェントへの指示も 1 か所で済むので便利なのですが、その分 1 つのリポジトリで必要になる言語とツールの種類が多くなります。

この記事では、それらをどう管理しているのかに加えて、エディタやコミット前のチェック、セキュリティ、インフラ、テストまで、実際に使っているツールや運用を紹介します。

# Dev Container で環境そのものを配る

Go・Node.js・OpenTofu・AWS CLI など必要なツールが多いので、各自のマシンにインストールしていく方式では、環境を揃えるだけで一苦労です。
OS の違いやツールのバージョン差で「自分の環境だけ動かない」が発生し、その調査に時間を取られてしまいます。

## イメージを配って全員同じ環境にする

そこで microCMS では **Dev Container** を使い、開発環境をコンテナイメージとして配布するようにしています。
リポジトリを clone してコンテナを開けば、それだけで全員が同じ環境になります。

コンテナイメージは CI でビルドして GitHub Container Registry に置いておき、各自はそれを pull するだけです。
イメージのビルドには時間がかかるので、全員が手元で同じビルドを繰り返さずに済みます。

副次的なメリットとして、ツールのインストールやシステム設定の変更はコンテナ内で完結するため、ホストの開発環境を汚しません。

これは、コーディングエージェントにコマンドを実行させるうえでも効いてきます。
意図しないコマンドでコンテナ内の環境が壊れても、コンテナを作り直せば元に戻せるので、開発用のコマンド実行を任せやすくなります。

依存やキャッシュの類は、Docker の名前付きボリュームに置いています。
`node_modules` や Go のビルドキャッシュ、mise で入れたツールに加えて、各種 CLI の認証情報も対象です。
コンテナを作り直しても、インストールし直しや再認証は発生しません。

## Cloud Agents でもほぼ同じイメージを使う

手元での開発とは別に、Cursor の [**Cloud Agents**](https://cursor.com/ja/cloud) も活用しています。
クラウド上のマシンでエージェントに作業させられるので、手元のマシンを占有せずに済みます。

こちらでも、ほぼ同じイメージを使っています。
ベースイメージこそ別に用意していますが、同じ `mise.toml` からツールを入れるので、手元とクラウドでツールが揃います。

# mise でツール・タスク・環境変数を管理する

開発ツールやタスクの管理には [**mise**](https://mise.jdx.dev/) を使っています。

公式では「One tool that manages dev tools, env vars, and tasks per project」と説明されており、その名のとおり開発ツール・環境変数・タスクをプロジェクト単位でまとめて管理できます。

## ツールのバージョンを固定する

microCMS では、言語ランタイムや Linter、IaC ツール、ターミナルで使う補助ツールなど、開発に使うものはすべて `mise.toml` に書いています。

```toml:mise.toml
# ここに載せているのは一例で、実際にはこれ以外のツールも並んでいます
[tools]
"go"                           = "x.y.z"
"node"                         = "x.y.z"
"npm:typescript"               = "x.y.z"
"npm:@biomejs/biome"           = "x.y.z"
"aqua:golangci/golangci-lint"  = "x.y.z"
"aqua:opentofu/opentofu"       = "x.y.z"
"aqua:gruntwork-io/terragrunt" = "x.y.z"
```

mise には aqua・npm・go・pipx といった取得元（バックエンド）が用意されています。
配布のされ方が違うツールでも、同じ `mise.toml` にまとめて書けます。

そして重要なのが、GitHub Actions でも同じ `mise.toml` からツールを入れていることです。
CI 用にバージョンを別管理する必要がなく、ローカルと CI で同じバージョンのツールを使えます。

「ローカルでは lint が通るのに CI では落ちる」といったバージョン差による問題も防げます。
ツールを追加するときも、`mise.toml` に 1 行足せばローカルにも CI にも入るので、更新漏れを防げます。

もちろん、コーディングエージェントも同じように管理しています。

```toml:mise.toml
[tools]
"npm:@anthropic-ai/claude-code" = "x.y.z"
"npm:@openai/codex"             = "x.y.z"
"cursor-cli"                    = "x.y.z"
```

:::message
Cursor CLI は npm などで配布されていないため、カスタムプラグインを用意してインストールできるようにしています。
:::

## コマンドの入口を 1 つにする

mise はタスクランナーとしても使えます。
microCMS では、開発サーバーの起動・デプロイ・テスト・環境の作成や削除まで、一通りのコマンドをタスクとして定義しています。

モノレポだと「web はこのコマンド、backend はこのコマンド」と入口が散らばりがちですが、すべて `mise run` から実行できるようにしているので、覚えるのは `mise run` だけで済みます。
※ `mise run` は毎回打つには長いので、`task` というエイリアスからも実行できるようにしています。

さらに、タスク名を覚えなくても済むように **fzf** を組み合わせています。

mise にはタスクが指定されなかったときに実行される `default` タスクを定義できるので、ここで fzf を起動してタスクを選ばせるようにしました。
`mise run` とだけ打てば、一覧から絞り込んで選択・実行できます。

![mise run で fzf を起動し、タスクを選択している様子](/images/microcms-dev-environment/mise-run-fzf.png)

:::message
スクリーンショットに写っているタスクは、説明用に用意したサンプルです。
実際に microCMS で定義しているタスクとは異なります。
:::

キーワードを入力すればあいまい検索で絞り込めるので、目的のタスクにすぐたどり着けます。
タスクには説明文を書けるため、選択画面には説明文も表示されます。

説明文つきのタスク一覧は、コーディングエージェントにも効いてきます。
ルールには細かい実行手順ではなく「タスク一覧を確認する」とだけ書いておけば、あとは一覧を見て適切なタスクを実行してくれます。

## 環境変数も mise から読み込む

mise は dotenv と同じように `.env` を読み込めるので、環境変数もここに寄せています。
シェルの設定に書いたり、ターミナルを開くたびに `export` したりする必要がありません。

ただ `.env` に置いているのは、どの環境を使うかといった設定が中心です。
シークレットはローカルに置かない方針にしていて、必要なものはタスクの実行時に取得し、使い終わったら破棄しています。

# エディタは Cursor がメイン、Neovim も使える

microCMS では **Cursor** を導入しており、エディタは Cursor を使っている人がほとんどです。
Dev Container に対応しているので、リポジトリを開くだけでコンテナに接続して開発を始められます。

一方で、ターミナルで完結させたい人向けに **Neovim** も用意しています。
Neovim 本体も mise で管理しているので、コンテナに入ればすぐ使えます。

ターミナルマルチプレクサの **herdr** や、Git 操作の **lazygit** といったツール、各言語の LSP なども mise で入れてあるので、ターミナルでの作業も効率よく進められます。

# git worktree や Cloud Agents で複数の作業を並行して進める

開発をしていると、複数の作業を同時に進めたい場面がよくあります。
そのときは git worktree で作業ディレクトリを分けたり、前述の Cursor の Cloud Agents を並行で動かしたりしています。
後述の「開発者ごとの環境」も worktree 単位で立てられるので、AWS 上のリソースまで含めて作業を分けられます。

worktree まわりは Dev Container 側でも整理していて、作成から後片付けまでを手間なく行えるようにしています。

# lefthook でコミット前にチェックする

Git hooks の管理には [**lefthook**](https://lefthook.dev/) を使っています。

各自が `.git/hooks` を設定する必要がなく、設定ファイルをリポジトリで共有できるのが利点です。
lefthook 自体も mise で管理しているので、バージョンも揃います。

pre-commit では、変更されたファイルに対して formatter や linter を並列で実行しています。
対象のファイルが無ければスキップされるので、モノレポでも待ち時間が伸びにくいです。

一方で、時間のかかるチェックは pre-commit に入れず、GitHub Actions 側に寄せています。
コミットのたびに数十秒待たされると、開発体験が一気に悪くなるためです。

# セキュリティを固める

ツールのバージョンを揃えるのと同じくらい気にしているのが、そもそも安全なパッケージを入れているかという点と、AWS へのアクセスをどう扱うかという点です。

npm のパッケージが乗っ取られ、悪意のあるコードが混入する事件は何度も起きています。
インストール時に実行されるスクリプトに悪意のある処理が含まれている場合、インストールした時点で実行される可能性があり、後からコードレビューで気づくのでは手遅れです。

## Takumi Guard で悪性パッケージをブロックする

microCMS では、npm・PyPI・Go モジュールの取得を [**Takumi Guard**](https://flatt.tech/takumi/features/guard) 経由にしています。
これはパッケージマネージャーと本家レジストリの間に入るプロキシで、インストール時に悪性パッケージを検知してブロックしてくれます。

```toml:mise.toml
[env]
NPM_CONFIG_REGISTRY = "https://npm.flatt.tech"
UV_DEFAULT_INDEX    = "https://pypi.flatt.tech/simple/"
GOPROXY             = "https://golang.flatt.tech"
```

参照先を書くだけで有効になるので、普段のコマンドは何も変わりません。

## 更新は Renovate に任せる

古い依存を放置するのも、それはそれでリスクです。

microCMS では [**Renovate**](https://docs.renovatebot.com/) を使い、依存関係の更新 PR を自動で作るようにしています。
npm のパッケージだけでなく、`mise.toml` のツールや GitHub Actions のバージョンまで対象にしているので、更新漏れが起きません。

更新の量が多くなりがちなので、グルーピングして PR が細かく分かれすぎないようにしています。

## 公開直後のバージョンを避ける

乗っ取られたパッケージは、公開されてから発覚・削除されるまでの間に被害が広がります。
そこで npm では、`.npmrc` に公開から一定期間が経過していないバージョンを使わない設定を入れています。
あわせて、インストール時のスクリプト実行も無効にしています。

```ini:.npmrc
min-release-age=8
ignore-scripts=true
```

mise にも同じ待機期間を設定しています。

```toml:mise.toml
[settings]
minimum_release_age = "8d"
```

ただし、mise では明示的に固定したツールのバージョンは対象外です。
npm・pipx バックエンドでは、ツールが内部で利用するパッケージに適用されます。

microCMS では `mise.toml` のバージョンを固定し、Renovate で更新しているため、Renovate 側にも待機期間を設定しています。

```json:renovate.json
{
  "minimumReleaseAge": "8 days"
}
```

これにより、npm のインストール時だけでなく、mise で入れるツールの内部依存や Renovate が更新する固定バージョンについても、公開直後のものをすぐに取り込まずに済みます。

## AWS へのアクセスは IAM Identity Center で

AWS へのアクセスには **IAM Identity Center** を使っています。
長期のアクセスキーを配らずに済むので、手元に残るのは期限付きの認証情報だけです。

AWS の認証が必要なタスクは、`aws sso login` を挟んでから実行するようにしてあるので、開発者がログインを意識する必要はありません。
権限は開発者をグループに分けて割り当てているので、担当に応じて触れる範囲を変えられます。

## シークレットはローカルに置かない

前述のとおり、環境変数は `.env` に置いていますが、シークレットは含めていません。
必要なものはタスクの実行時に取得し、使い終わったら破棄しています。

# インフラはすべて OpenTofu と Terragrunt でコード化する

microCMS のインフラは、すべて [**OpenTofu**](https://opentofu.org/) と [**Terragrunt**](https://terragrunt.gruntwork.io/) で管理しています。

「ここだけマネジメントコンソールで手作業」という例外は作らないようにしています。
コード化されていない部分が 1 つでもあると、環境を作り直すたびに手順書を見ながら手作業する必要が出てきてしまいます。

## なぜ OpenTofu なのか

AWS CDK を使っていないのは、AWS 以外に Cloudflare や OpenSearch の内部設定もまとめて管理しているからです。

そのうえで Terraform ではなく OpenTofu を採用しているのには、いくつか理由があります。

### プロバイダのキャッシュを設定なしで効かせられる

後述しますが、インフラの構成は Terragrunt でユニット単位に分割しています。
ユニットが増えてくると、同じプロバイダを何度もダウンロードすることになり、時間もディスクも消費します。

Terragrunt には以前から [Provider Cache Server](https://docs.terragrunt.com/features/provider-cache-server/) という機能があり、これを使えばプロバイダの実体を 1 つに抑えられます。
ただ、ローカルにプロキシとなるサーバーを立て、ユニットごとに CLI の設定ファイルを生成してリクエストの向き先を差し替える、という仕組みです。
そのため多数のユニットをまとめて実行するときは効く一方、単発の実行ではサーバーの起動コストの分、かえって遅くなることもあります。

一方 OpenTofu を使っている場合は、[Automatic Provider Cache Dir](https://docs.terragrunt.com/features/caching/auto-provider-cache-dir/) が使えます。
こちらは OpenTofu 本体が持つキャッシュの仕組みを Terragrunt が自動で設定してくれるもので、サーバーを立てる必要がありません。
設定なしで有効になり、単発の実行でもオーバーヘッドが乗りません。

### tfstate をクライアントサイドで暗号化できる

tfstate には秘匿情報が含まれることがあるため、暗号化は必須です。

Terraform でも S3 バックエンドのサーバーサイド暗号化は使えますが、これはバックエンドに届いてから暗号化される方式です。
OpenTofu の [state 暗号化](https://opentofu.org/docs/language/state/encryption/)は、手元で暗号化してからバックエンドに送るため、バックエンド側の暗号化だけに依存せず tfstate を保護できます。

## Terragrunt で構成を分割する

インフラを 1 つの大きな構成として書いてしまうと、少し変更するだけでも全体に対して plan / apply が走り、時間も影響範囲も大きくなります。

そこで Terragrunt を使い、ネットワーク・DB・API といった単位（ユニット）に分割しています。
普段は変更したユニットだけを対象にできるので、確認のサイクルが短くなります。

分割すると今度は、tfstate の保存先やプロバイダの定義といった設定が各ユニットで重複しますが、Terragrunt は共通の設定から自動で生成してくれます。
ユニット間の依存関係も解決してくれるので、まとめて実行するときの順序を自分で管理する必要もありません。

## 開発者ごとの環境をワンコマンドで作る

すべてがコードになっている一番のメリットは、環境を何度でも作り直せることです。

microCMS では、開発者が自分専用の環境を持てるようにしています。
共有の開発環境だけだと、「誰かが検証している間は触れない」という待ちが発生してしまうためです。

環境の作成はタスク化してあるので、コマンド 1 つでフロントエンドからバックエンド、インフラまで一式が AWS 上に立ち上がります。
不要になったら、こちらもコマンド 1 つで丸ごと削除できます。

スペックこそ違うものの、本番とほとんど同じ環境が立ち上がります。

これができるのは、アプリケーションのビルドとデプロイも Terragrunt のユニットとして定義しているからです。
「インフラは OpenTofu、デプロイは別のツール」と分かれていないので、環境を丸ごと作るときも 1 コマンドで完結します。

「壊してもすぐ作り直せる」状態になっていると、検証のハードルが下がります。

## アプリは AWS 上でも手元でも動かせる

実際に動かすときは、AWS 上のものをそのまま使う場合と、React・Go・Node.js・GraphQL の各サーバーを手元で立ち上げて自分の環境につなぐ場合の 2 通りがあります。

普段の実装は反映が速い手元のサーバーで進め、実際の経路やほかのサービスとの連携まで確かめたいときは AWS 上の環境を使います。

どちらもファイルの変更を監視するタスクを用意しているので、AWS 上へのデプロイも手元のサーバーの再起動も、自動で行うことができます。

# テストはサイズごとに分けて回す

microCMS では、テストを [Google のテストサイズ](https://testing.googleblog.com/2010/12/test-sizes.html)（Small / Medium / Large）の考え方にならって分類しています。

- **Small** — 外部依存をすべてモックにして、プロセス内で完結させるテスト
- **Medium** — DB や検索エンジンなど、ローカルに立てた実物を使うテスト
- **Large** — 実際にデプロイされた環境に対して実行するテスト

サイズが違えば、必要な準備も実行時間も変わります。
すべてを一括りにしてしまうと、ちょっとした修正の確認にまで重い準備が必要になってしまうので、サイズごとに分けて実行できるようにしています。

どのサイズもタスク化してあるので、実行自体は `mise run` から行えます。

## Small テストは手元でも CI でも常に回す

Small テストは外部依存をすべてモックにしているので、追加の準備なしにそのまま実行できます。

手元では lefthook の pre-push で、変更したファイルに関連するテストだけを実行しています。
毎回すべてを流すと待ち時間が長くなるので、関連するものに絞っています。

CI では PR ごとに実行しますが、こちらも変更のあったディレクトリだけを対象にしています。
モノレポなので、フロントエンドだけの変更でバックエンドのテストまで回すのは無駄になるためです。

## Medium テストは Floci 上で回す

DynamoDB や OpenSearch を実際に叩く Medium テストは、本物の AWS ではなく [**Floci**](https://floci.io/) と OpenSearch を Docker Compose で立ち上げて実行しています。

テーブルやインデックスの作成にも、本番と同じ OpenTofu / Terragrunt の構成をそのまま使っています。
エンドポイントをローカル向けに切り替えるだけで、必要なインフラを apply できます。
テスト用に別のスキーマ定義を持ちたくない、という意図です。

コンテナの起動から apply、テストの実行までをまとめてタスクにしてあるので、実行は 1 コマンドで済みます。
終わったらコンテナも構成ファイルも片付けるようにしてあります。

CI でも同じ仕組みをそのまま動かしていて、バックエンドやテーブル定義に変更があった PR で実行されます。
コンテナを立ち上げて apply する分時間がかかるので、Small テストのように常に回すことはしていません。

## Large テストは Playwright で回す

Large テストは、実際にデプロイされた環境の管理画面を操作する E2E テストです。
[**Playwright**](https://playwright.dev/) で書いていて、ステージング環境などに対して実行します。

これだけは PR ごとには実行していません。
対象の環境にデプロイされていることが前提になるうえ、実行にも時間がかかるためです。
そのため、デプロイのタイミングで自動的に起動し、結果を Slack のスレッドに通知するようにしています。

もちろん、確認したいときには手元からも実行できます。

# まとめ

今回紹介したツールや機能は次のとおりです。

- **Dev Container** — 開発環境をコンテナイメージとして配布する
- **mise** — ツールのバージョン・タスク・環境変数をプロジェクト単位で管理する
- **Cursor / Neovim** — エディタは Cursor がメイン、ターミナルで完結させたい人向けに Neovim も用意する
- **Cursor Cloud Agents** — クラウド環境でエージェントに作業させる
- **git worktree** — 作業ディレクトリを分けて並行作業する
- **lefthook** — Git hooks をリポジトリで共有し、コミット前チェックを行う
- **Takumi Guard** — npm / PyPI / Go モジュールの悪性パッケージをインストール時にブロックする
- **Renovate** — 依存関係の更新 PR を自動作成する
- **OpenTofu / Terragrunt** — インフラをすべてコード化し、開発者ごとの環境を再現可能にする
- **Floci** — AWS 互換環境をコンテナで立ち上げ、Medium テストを実行する
- **Playwright** — 管理画面の E2E（Large）テストを実行する

# おわりに

ここまで、microCMS で実際に使っている開発環境を紹介しました。

リモートワークなので、環境の違いでつまずくと隣で見てもらうこともできず、時間が溶けてしまいます。
その分、環境を揃える仕組みにはそれなりに手を入れています。
その結果として、手元でも CI でもエージェントでも、同じ土台の上で開発を進められるようになっています。

開発環境の話は地味になりがちですが、日々の開発体験には直結するので、興味のある方の参考になればと思います。
