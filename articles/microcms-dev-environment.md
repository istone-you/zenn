# はじめに

今回は、microCMS の開発環境について紹介します。

microCMS では、バックエンド（Go / Node.js）もフロントエンド（TypeScript）もインフラ（OpenTofu）も、1 つのモノレポで管理しています。
1 つのリポジトリで完結するのは便利なのですが、そのぶん 1 つのリポジトリで必要になる言語とツールの種類が多くなります。

この記事では、それらをどう管理しているのか、実際に使っているツールと運用を紹介します。

# Dev Container で環境そのものを配る

Go・Node.js・Python・OpenTofu・AWS CLI……と必要なツールが多いので、各自のマシンにインストールしていく方式は早々に無理が来ます。
OS の違いやツールのバージョン差で「自分の環境だけ動かない」が発生し、その調査に時間を取られてしまいます。

## イメージを配って全員同じ環境にする

そこで microCMS では **Dev Container** を使い、開発環境をコンテナイメージとして配布するようにしています。
リポジトリを clone してコンテナを開けば、それだけで全員が同じ環境になります。

コンテナイメージは CI でビルドして GHCR に置いておき、各自はそれを pull するだけです。
イメージのビルドには時間がかかるので、全員が手元で同じビルドを繰り返さずに済みます。

副次的なメリットとして、環境を壊しても作り直せば元に戻せます。

これは、コーディングエージェントにコマンドを実行させるうえでも効いてきます。
影響範囲がコンテナ内に閉じるので、権限を絞りすぎずに作業を任せられます。

## Cloud Agent でもほぼ同じイメージを使う

手元での開発とは別に、Cursor の Cloud Agent も活用しています。
クラウド上のマシンでエージェントに作業させられるので、手元のマシンを占有せずに済みます。

こちらでも、ほぼ同じイメージを使っています。
ベースイメージこそ別に用意していますが、同じ `mise.toml` からツールを入れるので、手元とクラウドでツールが揃います。

# mise でツール・タスク・環境変数を管理する

開発ツールやタスクの管理には [**mise**](https://mise.jdx.dev/) を使っています。

公式では「One tool that manages dev tools, env vars, and tasks per project」と説明されており、その名のとおり開発ツール・環境変数・タスクをプロジェクト単位でまとめて管理できます。

## ツールのバージョンを固定する

microCMS では、言語ランタイムも Linter も IaC ツールも、すべて `mise.toml` に書いています。

```toml:mise.toml
[tools]
"go"            = "x.y.z"
"node"          = "x.y.z"
"typescript"    = "x.y.z"
"opentofu"      = "x.y.z"
"terragrunt"    = "x.y.z"
"golangci-lint" = "x.y.z"
"biome"         = "x.y.z"
```

そして重要なのが、GitHub Actions でも同じ `mise.toml` からツールを入れていることです。
CI 用にバージョンを別管理する必要がなく、ローカルと CI で必ず同じツールが使われます。

「ローカルでは lint が通るのに CI では落ちる」といったバージョン差による問題も起きません。
ツールを追加するときも、`mise.toml` に 1 行足せばローカルにも CI にも入るので、更新漏れが起きません。

もちろん、コーディングエージェントも同じように固定しています。

```toml:mise.toml
[tools]
"claude-code" = "x.y.z"
"codex"       = "x.y.z"
"cursor-cli"  = "x.y.z"
```

:::message
Cursor CLI は npm などで配布されていないため、そのままでは mise で扱えません。
そこで、インストール処理を書いた自前のプラグインをリポジトリ内に置き、`mise plugins link` で登録して使えるようにしています。
:::

更新の速い領域なので、「自分の手元だけバージョンが古い」といったことが起きやすいのですが、それも防げます。

## コマンドの入口を 1 つにする

mise はタスクランナーとしても使えます。
microCMS では、開発サーバーの起動・デプロイ・テスト・環境の作成や削除まで、ひととおりのコマンドをタスクとして定義しています。

モノレポだと「web はこのコマンド、backend はこのコマンド」と入口が散らばりがちですが、すべて `mise run` から実行できるようにしているので、覚えるのは `mise run` だけで済みます。
※ `mise run` は毎回打つには長いので、`task` というエイリアスからも実行できるようにしています。

さらに、タスク名を覚えなくても済むように **fzf** を組み合わせています。

mise にはタスクが指定されなかったときに実行される `default` タスクを定義できるので、ここで fzf を起動してタスクを選ばせるようにしました。
`mise run` とだけ打てば、一覧から絞り込んで選択・実行できます。

![mise run で fzf を起動し、タスクを選択している様子](/images/microcms-dev-environment/mise-run-fzf.png)

:::message
スクリーンショットに写っているタスクは、説明用に用意したサンプルです。
実際に microCMS で定義しているタスクとは異なります。
:::

`terraform:` のようなプレフィックスで絞り込むこともできるので、目的のタスクにすぐたどり着けます。
タスクには説明文を書けるため、選択画面には説明文も表示されます。

README にコマンドを書き写して更新が止まる、ということも起きません。

これはコーディングエージェントに対しても同じです。
ルールには細かい実行手順ではなく「タスク一覧を確認する」とだけ書いておけば、あとは一覧を見て適切なタスクを実行してくれます。

## 環境変数も mise から読み込む

mise は `.env` を読み込めるので、環境変数もここに寄せています。
シェルの設定に書いたり、ターミナルを開くたびに `export` したりする必要がありません。

`.env` に置いているのは、どの環境を使うかといった設定が中心です。
一方でシークレットはローカルに置かない方針にしていて、必要なものはタスクの実行時に取得し、使い終わったら破棄しています。

# エディタは Cursor がメイン、Neovim も使える

エディタは **Cursor** を使っている人がほとんどです。
Dev Container に対応しているので、リポジトリを開くだけでコンテナに接続して開発を始められます。

一方で、ターミナルで完結させたい人向けに **Neovim** も用意しています。
Neovim 本体も mise で管理し、設定一式をリポジトリに入れているので、コンテナに入ればすぐ使えます。

ターミナルマルチプレクサの **herdr** や、Git 操作の **lazygit** といったツール、各言語の LSP なども mise で入れてあるので、ターミナルでの作業も効率よく進められます。

# コミット前のチェックは lefthook で

Git hooks の管理には [**lefthook**](https://lefthook.dev/) を使っています。

各自が `.git/hooks` を設定する必要がなく、設定ファイルをリポジトリで共有できるのが利点です。
lefthook 自体も mise で管理しているので、バージョンも揃います。

pre-commit では、変更されたファイルに対して formatter や linter を並列で実行しています。
対象のファイルが無ければスキップされるので、モノレポでも待ち時間が伸びにくいです。

一方で、時間のかかるチェックは pre-commit に入れず、GitHub Actions 側に寄せています。
コミットのたびに数十秒待たされると、開発体験が一気に悪くなるためです。

コミット前に弾きたいのは「明らかな間違い」だけで、それ以外は CI に任せる、という切り分けにしています。

# 依存まわりのセキュリティ

ツールのバージョンを揃えるのと同じくらい気にしているのが、そもそも安全なパッケージを入れているかという点です。

npm のパッケージが乗っ取られ、悪意のあるコードが混入する事件は何度も起きています。
インストールした時点で実行されてしまうため、後からコードレビューで気づくのでは手遅れです。

## 悪性パッケージをブロックする

microCMS では、npm・PyPI・Go モジュールの取得を [**Takumi Guard**](https://flatt.tech/takumi/features/guard) 経由にしています。
これはパッケージマネージャーと本家レジストリの間に入るプロキシで、インストール時に悪性パッケージを検知してブロックしてくれます。

```toml:mise.toml
NPM_CONFIG_REGISTRY = "https://npm.flatt.tech"
UV_DEFAULT_INDEX    = "https://pypi.flatt.tech/simple/"
GOPROXY             = "https://golang.flatt.tech"
```

参照先を書くだけで有効になるので、普段のコマンドは何も変わりません。

## 公開直後のバージョンを避ける

乗っ取られたパッケージは、公開されてから発覚・削除されるまでが勝負です。
そこで npm では、`.npmrc` に公開から一定期間が経過していないバージョンを使わない設定を入れています。
あわせて、インストール時のスクリプト実行も無効にしています。

```ini:.npmrc
# 公開直後の依存を避ける
min-release-age=8
# パッケージのインストール時にスクリプトを実行しない (postinstall, preinstallなど)
ignore-scripts=true
```

mise にも同じ設定があるので、mise で入れるツールにも効かせています。

```toml:mise.toml
[settings]
minimum_release_age = "8d"
```

これだけでも、被害に遭う確率を下げられます。

## 更新は Renovate に任せる

古い依存を放置するのも、それはそれでリスクです。

microCMS では [**Renovate**](https://docs.renovatebot.com/) を使い、依存関係の更新 PR を自動で作るようにしています。
npm のパッケージだけでなく、`mise.toml` のツールや GitHub Actions のバージョンまで対象にしているので、更新漏れが起きません。

更新の量が多くなりがちなので、グルーピングして PR が細かく分かれすぎないようにしています。

# インフラはすべて OpenTofu と Terragrunt でコード化する

microCMS のインフラは、すべて [**OpenTofu**](https://opentofu.org/) と [**Terragrunt**](https://terragrunt.gruntwork.io/) で管理しています。

ポイントは、「ここだけマネジメントコンソールで手作業」という例外を作らないことです。
コード化されていない部分が 1 つでもあると、環境を作り直すたびに手順書を見ながら手作業する必要が出てきてしまいます。

## なぜ Terraform ではなく OpenTofu なのか

Terraform ではなく OpenTofu を採用しているのには、いくつか理由があります。

### プロバイダのキャッシュを設定なしで効かせられる

後述のとおり、インフラの構成は Terragrunt でユニット単位に分割しています。
ユニットが増えてくると、同じプロバイダを何度もダウンロードすることになり、時間もディスクも消費します。

Terragrunt には以前から [Provider Cache Server](https://docs.terragrunt.com/features/provider-cache-server/) という機能があり、これを使えばプロバイダの実体を 1 つに抑えられます。
ただ、ローカルにプロキシとなるサーバーを立て、ユニットごとに CLI の設定ファイルを生成してリクエストの向き先を差し替える、という仕組みです。
そのため多数のユニットをまとめて実行するときは効く一方、単発の実行ではサーバーの起動コストのぶん、かえって遅くなることもあります。

一方 OpenTofu を使っている場合は、[Automatic Provider Cache Dir](https://docs.terragrunt.com/features/caching/auto-provider-cache-dir/) が使えます。
こちらは OpenTofu 本体が持つキャッシュの仕組みを Terragrunt が自動で設定してくれるもので、サーバーを立てる必要がありません。
設定なしで有効になり、単発の実行でもオーバーヘッドが乗りません。

### tfstate をクライアントサイドで暗号化できる

tfstate には秘匿情報が含まれることがあるため、暗号化は必須です。

Terraform でも S3 バックエンドのサーバーサイド暗号化は使えますが、これはバックエンドに届いてから暗号化される方式です。
OpenTofu の [state 暗号化](https://opentofu.org/docs/language/state/encryption/)は、手元で暗号化してからバックエンドに送るので、ローカルに残るファイルや CI 上のアーティファクトも暗号化された状態になります。

暗号鍵には AWS KMS を指定できるので、鍵の管理も既存の仕組みに寄せられます。

## Terragrunt で構成を分割する

インフラを 1 つの大きな構成として書いてしまうと、少し変更するだけでも全体に対して plan / apply が走り、時間も影響範囲も大きくなります。

そこで Terragrunt を使い、ネットワーク・DB・API といった単位（ユニット）に分割しています。
普段は変更したユニットだけを対象にできるので、確認のサイクルが短くなります。

分割すると今度は、tfstate の保存先やプロバイダの定義といった設定が各ユニットで重複しますが、Terragrunt は共通の設定から自動で生成してくれます。
ユニット間の依存関係も解決してくれるので、まとめて実行するときの順序を自分で管理する必要もありません。

## 開発者ごとの環境をワンコマンドで作る

すべてがコードになっている一番のメリットは、環境を何度でも作り直せることです。

microCMS では、開発者が自分専用の環境を持てるようにしています。
共有の開発環境だけだと、「誰かが検証している間は触れない」という待ちが発生してしまうためです。

環境の作成はタスク化してあるので、コマンド 1 つでフロントエンドからバックエンド、インフラまで一式が AWS 上に立ち上がります。
不要になったら、こちらもコマンド 1 つで丸ごと削除できます。

これができるのは、アプリケーションのビルドとデプロイも Terragrunt のユニットとして定義しているからです。
「インフラは OpenTofu、デプロイは別のツール」と分かれていないので、環境を丸ごと作るときも 1 コマンドで完結します。

ビルドはソースコードのハッシュを見て、変更があったユニットだけが実行されるようにしています。
そのため、2 回目以降は変更した箇所だけがビルド・デプロイされます。

「壊してもすぐ作り直せる」状態になっていると、検証のハードルが下がります。

# おわりに

改めて振り返ると、やっていることはシンプルです。

- 開発環境はコンテナイメージとして配布する
- ツールのバージョンは固定する
- コマンドの入口は 1 つにする
- インフラはすべてコード化して、いつでも作り直せるようにする

いずれも特別なことではありませんが、モノレポで扱う対象が増えるほど効いてきます。
そして、こうして整えた環境はそのまま AI エージェントの実行環境にもなります。

同じような構成で悩んでいる方の参考になれば幸いです。
